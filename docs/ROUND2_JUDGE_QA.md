# AURA-IMPACT: COMPREHENSIVE JUDGE Q&A DEFENSE BRIEF

**Document Reference:** `docs/ROUND2_JUDGE_QA.md`  
**Purpose:** Technically defensible, evidence-grounded answers to hostile questions from automotive engineering judges at KPIT Sparkle Round 2.

---

### 1. Why not graph-only?
**Answer:**  
Graph-only analysis relies strictly on explicit, pre-existing edges (e.g., links in `.arxml` or ALM tools like DOORS/Polarion). In modern agile vehicle software integration, traceability is frequently incomplete, broken, or lagging behind active C implementation changes. 

In our validated research benchmark across 150 automated mutation batches, Graph-Only achieved an Artifact F1 of 0.4557 and **failed to maintain the safety invariant** (achieving only 98.67% retention because broken links caused safety-critical components to be missed). In our live demonstration (Scenario 2), when an explicit link is missing, Graph-Only reports **0% impact**—a critical safety defect.

---

### 2. Why not an LLM?
**Answer:**  
Large Language Models (LLMs) are unsuitable for real-time, deterministic automotive CI/CD for four reasons:
1. **Non-Determinism:** LLMs lack formal mathematical reproducibility required by ISO 26262 audits; identical prompts can yield varying test selections.
2. **Hallucination & Lack of Constraints:** LLMs generate cross-subsystem false positives based on superficial semantic similarities (e.g., linking cabin HVAC temperature controls to high-voltage battery thermal management).
3. **Execution Latency & Cost:** Commercial LLM API calls take 1,500 ms to 5,000 ms per query, whereas AURA-Impact executes in **5.34 ms** locally.
4. **Data Sovereignty:** OEMs strictly prohibit sending unreleased software architecture and source code to third-party cloud LLM APIs.

---

### 3. Why not embeddings alone?
**Answer:**  
Unconstrained vector embeddings suffer from catastrophic precision collapse in technical domains. In our benchmark, Embedding-Only achieved an Artifact Precision of 66.78% on simple text, but its Artifact Recall plummeted to **42.45%** with an abysmal Artifact F1 of **0.3114**. 

Vector embeddings lack structural awareness: they do not understand port connections, call graphs, or ECU bus boundaries. In Scenario 3, pure embedding retrieval flags `SWC_BodyLightController` simply because it contains words like *"deceleration brake light warning"*, creating expensive false alarms.

---

### 4. What exactly is novel?
**Answer:**  
The novelty of AURA-Impact lies in the **formal synthesis of deterministic graph traversal with context-constrained semantic recovery, bounded by a mathematical safety gate**:
$$S_{final} = S_{struct} \cup S_{semantic}$$
Where $S_{semantic}$ is not an unconstrained nearest-neighbor search, but is filtered through a hard multi-dimensional architectural gate:
$$\text{ContextGate}(c) = \mathbb{I}(\text{Subsystem}(c) = \text{Subsystem}(a)) \land \mathbb{I}(\text{ECU}(c) = \text{ECU}(a)) \land \text{Compatible}(\text{Type}(c), \text{Type}(a))$$
Coupled with the formal invariant:
$$T_{safe} \subseteq T_{selected}$$
This ensures zero safety regressions while recovering unlinked dependencies.

---

### 5. How do you prevent semantic hallucinations?
**Answer:**  
Semantic candidates generated by `AURA-DomainHashEmbedder-384` are never added directly to the impact set. They must pass through the **Context Filter**, which applies hard, non-negotiable engineering constraints:
- **Subsystem Isolation:** Candidates in different automotive domains (e.g., Infotainment vs. ADAS) are strictly rejected regardless of cosine similarity score.
- **ECU Boundary Checks:** Unless an explicit inter-ECU CAN/LIN/Ethernet interface is declared, intra-ECU components cannot link across distinct ECUs.
- **Interface Compatibility:** The candidate must exhibit compatible port types (Sender-Receiver vs. Client-Server).

---

### 6. How does context filtering work?
**Answer:**  
The Context Filter evaluates a candidate artifact $c$ against the changed artifact $a$ using four deterministic rules:
1. `Subsystem(c) == Subsystem(a)`: Enforces domain isolation.
2. `ECU(c) == ECU(a)` or `HasCrossECUBusBinding(c, a)`: Enforces electronic hardware boundaries.
3. `ArtifactCompatibility(Type(c), Type(a))`: Ensures logical transitions (Requirement $\rightarrow$ Component $\rightarrow$ Code $\rightarrow$ Test).
4. `MinSimilarityThreshold`: The cosine similarity must exceed a pre-calibrated baseline (default 0.50).

If any check fails, the candidate is rejected, and the exact engineering violation is logged in the evidence trail.

---

### 7. How do you handle incomplete traceability?
**Answer:**  
AURA-Impact is specifically designed for incomplete traceability. When explicit links are present, Stage 1 captures them with deterministic certainty. When explicit links are broken or omitted, Stage 2 detects that structural reachability is incomplete and automatically activates contextual semantic recovery to span the gap.

---

### 8. How do you prove graph blindness?
**Answer:**  
Graph blindness is mathematically demonstrated whenever the shortest path distance in the explicit directed graph $G=(V,E)$ between changed artifact $u$ and impacted artifact $v$ is infinite:
$$d_G(u, v) = \infty$$
In Scenario 2, the edge $(REQ\_AEB\_SENSOR\_001, SWC\_AEB\_FusedTargetHandler)$ does not exist in the `.arxml` graph. Stage 1 BFS returns $S_{struct} = \emptyset$. However, the runnable actually processes the sensor requirement's data signals. AURA-Impact recovers it via contextual semantics, proving recovery from graph blindness.

### 9. How do you prevent data leakage?
**Answer:**  
As formally documented in `validation/round2/leakage_audit.md`:
1. **Prediction Independence:** The impact analysis pipeline (`pipeline.py`, `impact_engine.py`, `retriever.py`) never accepts, imports, or references benchmark ground-truth labels during execution.
2. **Post-Hoc Evaluation Only:** Ground truth is strictly loaded in separate evaluation harnesses (`src/benchmark/metrics.py`) *after* predictions are generated.
3. **Curated Demonstration Dataset:** The demonstration dataset (`data/demonstration_dataset/`) is physically separated from benchmark evaluation corpora.

---

### 10. How is ground truth generated?
**Answer:**  
In our research benchmark, ground truth was generated using synthetic mutation injection on formal AUTOSAR architectural topologies. Each mutation altered a specific signal, runnable, or parameter, and ground-truth dependencies were determined by exhaustive multi-hop reachability including hidden interface bindings verified against complete architectural specifications.

---

### 11. Why is the precision not higher (54.92% in benchmark)?
**Answer:**  
In safety-critical automotive systems under ISO 26262, **a false negative (missed impact) is catastrophic, while a false positive (running an extra test) merely costs compute time**. 

AURA-Impact intentionally tunes semantic sensitivity to favor recall over precision. A precision of 54.92% means that roughly 1 out of 2 predicted artifacts is a true impact, which enables an **82.29% reduction in test suite size** while achieving **90.07% test recall** and **100% safety invariant retention**. Keyword search, by contrast, had only 18.97% precision.

---

### 12. Why is semantic recall only 40.67% in the research benchmark?
**Answer:**  
The 40.67% figure represents the recall of **Embedding-Only retrieval when evaluated in complete isolation without graph traversal**. This proves our core thesis: *semantic retrieval alone cannot solve change impact analysis*. Only when fused with deterministic graph traversal ($S_{struct} \cup S_{semantic}$) does overall artifact recall reach **63.11%** and test suite recall reach **90.07%**.

---

### 13. Why does AURA sometimes equal contextual retrieval?
**Answer:**  
When structural graph links are entirely absent for a given change (such as in unlinked requirements or newly drafted components), $S_{struct} = \emptyset$. In that specific edge case:
$$S_{final} = \emptyset \cup S_{semantic} = S_{semantic}$$
In those scenarios, AURA-Impact's output is identical to its contextual semantic retrieval stage, demonstrating that the semantic fallback correctly carries the full analysis load when the graph fails.

---

### 14. Why is the prototype different from the benchmark?
**Answer:**  
The **Research Benchmark** evaluates 150 automated mutation batches over synthetic topological graphs to compute macro-statistical metrics (Recall, Precision, F1). 

The **Engineering Prototype / Demonstrator** is an end-to-end executable application with an interactive dashboard, C/ARXML parsers, a live 100-test regression selector, and human-in-the-loop audit logs. The benchmark validates the scientific hypothesis; the prototype demonstrates production feasibility.

---

### 15. How does the safety gate work?
**Answer:**  
The Safety Gate implements the subset condition $T_{safe} \subseteq T_{selected}$.
1. It queries the system test repository for all tests marked `ASIL_C` or `ASIL_D` that cover the impacted subsystem or ECU.
2. It compares this set $T_{safe}$ with the tests chosen by the test selector.
3. If any test $t \in T_{safe}$ is missing from $T_{selected}$, the gate **blocks** the exclusion, logs a safety violation alert, and forcefully re-inserts $t$ into $T_{selected}$.

---

### 16. What happens when the system is uncertain?
**Answer:**  
AURA-Impact refuses to guess. If the semantic retrieval confidence falls into the ambiguous zone (similarity between 0.35 and 0.50), or if interface bindings are contradictory, the engine outputs **`REVIEW_REQUIRED`**. It flags candidate components for systems engineer sign-off and conservatively falls back to executing baseline safety tests rather than risking silent omission.

---

### 17. How does this integrate with AUTOSAR?
**Answer:**  
AURA-Impact parses native AUTOSAR XML (`.arxml`) schemas, extracting:
- `APPLICATION-SW-COMPONENT-TYPE` (Software Components)
- `P-PORT-PROTOTYPE` and `R-PORT-PROTOTYPE` (Provided and Required Ports)
- `SENDER-RECEIVER-INTERFACE` and `CLIENT-SERVER-INTERFACE`
- `RUNNABLE-ENTITY` and internal behavior timing events.

These map directly into our deterministic engineering graph nodes and edges.

### 18. How does it integrate with CI/CD?
**Answer:**  
AURA-Impact runs as a lightweight CLI utility in pre-commit git hooks or CI runners (Jenkins, GitLab CI, GitHub Actions):
```bash
python scripts/run_round2_validation.py --diff HEAD~1
```
It returns an exit code of `0` on success and writes `selected_tests.json`, which is consumed directly by test runners like ctest, Vector CANoe, or dSPACE AutomationDesk.

### 19. What happens with proprietary automotive data?
**Answer:**  
AURA-Impact operates **100% offline and on-premise**. It uses deterministic domain feature hashing (`AURA-DomainHashEmbedder-384`) running in local CPU memory. No code, requirements, or architecture metadata ever leaves the OEM's internal network.

---

### 20. Can this run offline?
**Answer:**  
Yes. AURA-Impact has zero external cloud dependencies. It runs completely offline on air-gapped engineering workstations or secure internal build servers.

---

### 21. What happens when an artifact changes?
**Answer:**  
When an artifact changes, the ingestion engine computes its SHA-256 hash and updates its graph node and embedding vector. Downstream nodes within $k \le 3$ hops are invalidated. Incremental re-indexing takes less than 10 milliseconds.

---

### 22. How is stale data detected?
**Answer:**  
AURA-Impact compares the filesystem `mtime` and file content hash against the cached index manifest (`index_metadata.json`). If a file has been modified or deleted on disk after the index was generated, the pipeline flags `STALE_INDEX_DETECTED` and prompts an automatic incremental re-index (as validated in Scenario 8).

---

### 23. What happens with a new ECU or subsystem?
**Answer:**  
When a new ECU or subsystem is introduced, it is declared in the `.arxml` or system configuration. The Context Filter automatically reads the new metadata tag and establishes new isolation boundaries without requiring retraining or manual heuristic reprogramming.

---

### 24. How does it scale?
**Answer:**  
- **Graph Traversal:** $O(V + E)$ bounded at depth $k \le 3$, which scales linearly and takes $< 0.1 \text{ ms}$.
- **Semantic Retrieval:** $O(N \cdot D)$ where $D=384$ feature dimensions. For an enterprise repository of 10,000 artifacts, vectorized cosine similarity completes in $< 15 \text{ ms}$ on a standard CPU.
- In our validation (Scenario 10), analyzing a large project with 170+ tests and full component graphs took just **57.50 ms**.
